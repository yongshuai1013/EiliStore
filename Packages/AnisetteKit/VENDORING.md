SideStore-style runtime acquisition

- The existing User Customizations page exposes confirmation-gated acquisition using the selected Anisette catalog source (default `https://servers.sidestore.io/servers.json`) and an ODA fallback (default `https://zzz.haus/oda.json`). It accepts direct ODA metadata (`s`/`sha`/`sha256` with `l`/`libraries`/`payload`/`data`/`url`) containing inline Base64 ZIP or an HTTPS ZIP URL. It also accepts a server-list `oda` object or absolute/relative metadata path. Only absent ODA uses the fallback, not request, archive or validation failures; traversal is bounded to four metadata requests. Digest mismatch follows SideStore's warning-and-continue behavior.
- A well-formed SHA-256 is mandatory, but mismatch is advisory: it records a warning and continues extraction, matching SideStore. ZIP structure, CRC, size, ELF checks and transactional installation remain mandatory. The hash and payload location come from the SAME third-party metadata: this is an advisory integrity comparison, **not independently pinned authenticity**. The provider may change both. Source trust, legal availability and redistribution permission remain unverified; the UI discloses these boundaries before downloading.
- A cookie/credential/cache-free session bounds streamed metadata to 16 MiB and ZIP data to 64 MiB, rejects non-HTTPS URLs before requests and rejects HTTPS-to-HTTP redirects before following them. Redirects are limited to five. Only exact flat two-library or five-library regular-file sets are installed. The sole extra-file exception is a regular `__MACOSX/._<library>` companion for an actually included library; an optional unique empty, stored `__MACOSX/` directory is also accepted. Companions are streamed through the same size, cancellation and CRC checks, counted in the total expansion limit, then discarded without being written to disk. All other paths, duplicates, symlinks, mixed/incomplete sets and unknown extras are rejected; at most eleven entries are accepted. Uncompressed data is capped at 64 MiB per file and 128 MiB total, with chunk limits, explicit CRC comparison and bounded ELF64 LE/AArch64 shared-object headers for libraries.
- The observed default ODA ZIP contains two root libraries and two 163-byte macOS AppleDouble companions. Previously its four entries failed the exact two-or-five entry-count guard before extraction; that packaging mismatch was not proof of ZIP corruption. Regression fixtures recreate this layout and data descriptors using synthetic bytes only; no downloaded Apple binary is committed, packaged or published.
- Downloads stage in a unique private directory and reuse the existing serialized import transaction/rollback. Network or validation failure and cancellation do not replace the installed cache; temporary payloads are removed. An active local login blocks download before networking. Successful installation resets the local engine cache, but does not select On-Device, provision, create an identity, contact Apple or modify remote credentials.
- Read-only library/storage status and remote login never trigger retrieval. Local login may acquire missing libraries only after the user separately enables automatic acquisition in ODA management (off by default); invalid/incompatible sets are not silently replaced. A preflight-passing cache is reused without downloading or changing provisioning. Remote Anisette remains the default. A downloaded modern five-library set is still diagnostic-only and blocked by the existing Android ABI gate; retrieval does not resolve the 72 unimplemented imports in the examined 6.5.3 set.
- `Tests/run-adi-download-tests.sh` exercises the downloader with generated synthetic ZIPs; `Tests/run-anisette-tests.sh` injects synthetic staging to check installation, cancellation, cleanup, mode isolation and the active-session guard. Test dependency downloads are source tooling only, never Apple binary downloads. No runtime-downloaded Apple binary is added to source, CI artifacts or the IPA.

Guest synchronization and module-callback follow-up

- Uses the per-guest-address mapping approach from SideStore's pinned macOS host loader as a design reference, but does not pass guest pthread objects or callback pointers to Darwin. The iOS Unicorn VM has a single guest thread: bounded mutex/rwlock state lives inside that VM, not inside a host-thread-owned pthread lock. Default-null/default-zero attributes and all-zero static initializers are supported. Init/destroy, lock/unlock and try operations have explicit state transitions and Android errno values. Contended blocking operations stop with an unsupported-scheduler error; recursive/error-checking/process-shared attributes, condition variables, thread creation, TLS and once callbacks remain unsupported. Each lock-type map is limited to 4096 records, including destroyed tombstones; a destroyed slot can be explicitly reinitialized.
- Android LP64 mutex/rwlock storage is exactly 40/56 bytes, based on the [Bionic pthread types](https://android.googlesource.com/platform/bionic/+/refs/heads/main/libc/include/bits/pthread_types.h). Object ranges require readable/writable guest mappings, attrs require readable mappings, and malformed, overflowing or unaligned addresses stop execution. Initialization no longer blindly clears 64 bytes of adjacent memory. Guest ownership survives serial calls on different host threads; this does not make Unicorn safe for concurrent host execution.
- `dl_iterate_phdr` now snapshots the real loaded ELF program headers and invokes the callback through a self-authored ARM64 guest trampoline. No nested host `uc_emu_start` and no host callback to an untrusted address is used. It supplies the 32-byte Android LP64 `dl_phdr_info` prefix and advertises that size, not fabricated extended TLS/counter fields. Callback return values use W0/int semantics, stop iteration on nonzero, and preserve AAPCS64 callee-saved registers and stack. At most 64 mapped modules and 1024 program headers per module are accepted. Metadata/callback mappings, names, file spans and allocations are bounded; program headers are copied without unaligned host casts and BSS is initialized in small chunks.
- Self-authored assembly is retained in `Tests/Fixtures/synthetic-module-iteration.S` and `module-iteration-callbacks.S`; the matching embedded/generated words are checked with an ARM64 assembler during development. Native synthetic tests cover nested imports and finite nested module iteration, positive/negative callback results, garbage in X0's upper bits, exact-size canaries, static locks, invalid mappings, lock-state isolation and fail-closed contention. `Tests/run-anisette-native-tests.sh` includes these tests and generated-ELF bounds tests in the existing native CI job.
- Compared with the previously recorded five-library inventory, seven more names now have bounded explicit adapters, leaving 49 unimplemented symbols. This is only a static import-inventory comparison. The modern runtime gate and remote default remain; no Apple library was executed or redistributed, no account/device credentials were used, and no real iPhone login is claimed.

依照 SideStore 恢復未解析函式 fallback（第一階段；資料與相依庫策略由下方最新段落取代）

本次依使用者明確要求，恢復鎖定版本 SideStore/AnisetteKit 在未解析函式上的處理方式：先尋找真實 guest export 或明確 adapter；仍未解析的函式建立 guest RET stub，呼叫時將 X0 設為零後返回。未知函式不再僅因缺少 adapter 而中止。這項決定取代前段「未知強函式匯入一律停止」的策略，但不會將這些 stub 列入已實作 ABI 白名單。VM 另行記錄 fallback 名稱與呼叫次數，區分「只建立 stub」和「確實執行 fallback」。

Swift ELF 預檢同步區分可走此路徑的 STT_FUNC／非資料型 STT_NOTYPE 與資料／TLS 等非函式符號；只有未知函式時顯示相容 stub 警告，不再當作該原因的硬性阻擋。未知資料符號及 SideStore 原始碼識別的 vtable、RTTI、kCF 等資料名稱不建立函式 stub，也不捏造零填充物件。缺庫、入口、SONAME、重定位及新版 ABI gate 的限制保持不變；遠端 Anisette 仍為預設。

合成測試驗證的是此 fallback 行為本身、真實 export 優先、重複 stub 穩定性、弱符號及資料／TLS 分類；回傳零不等於該函式真的完成工作，更不是 Apple 登入證明。沒有執行或散布 Apple 函式庫，也沒有使用帳號憑證或操作使用者的 iPhone。另外修正 CI 中仍假設兩個 provider 使用相同 header 字串的過時斷言，改為驗證本機 override 加入保存 routing-info 後仍傳遞至 provider。

Mobile VM startup crash-risk follow-up

- Pressing login in local mode eventually constructs `EmulatorVM`; `uc_open` is lazy and the first `uc_mem_map` initializes the pinned Unicorn TCG engine. Its 64-bit default translation buffer is 1 GiB (`qemu/accel/tcg/translate-all.c`, `size_code_gen_buffer`), and `code_gen_alloc` calls `exit(1)` when that host mapping fails. The previous EiliStore constructor did not override it, in addition to mapping a 512 MiB guest heap and 16 MiB guest stack. The C++ exception boundary cannot catch `exit(1)` or an OS memory-pressure termination.
- EiliStore now sets an 8 MiB TCG buffer immediately after `uc_open`, BEFORE any initializing API, and uses a 32 MiB guest heap and 2 MiB guest stack. These are startup budgets, not a total-process resident-memory cap: libraries, translation metadata and other allocations still consume memory. Heap exhaustion returns null and may cause the local operation to fail; no automatic remote fallback is introduced. Remote remains the default. No Android ABI/TLS support is claimed by this change.
- Guest malloc/realloc padding and calloc multiplication are checked for overflow. A failed guest calloc/realloc no longer proceeds to allocate a host vector; calloc writes zeroes in 4 KiB chunks. These are bounded-allocation fixes, not a complete Android malloc/free/realloc implementation (the existing bump allocator still does not reclaim freed allocations).
- `NativeVMStartupTests.cpp` starts a fresh process, checks the actual TCG setting and heap/stack mappings, and runs self-authored ARM64 `mov w0,#42; ret`. On Linux it lowers only the soft `RLIMIT_AS` to at most 256 MiB. A separate temporary comparison of bd69d30 against this patch under that same limit reproduced old startup exiting with code 1 and `Could not allocate dynamic translator buffer`, versus new startup returning 42. This establishes a host startup failure mechanism, NOT that the user's iPhone termination had that cause. macOS skips the unsupported address-space cap but executes the same native startup/ABI tests. CI now runs the synthetic native suite on both Linux and macOS in addition to the unsigned iOS archive.
- Without the iPhone crash report, the direct cause of the reported #395 termination is unconfirmed. Relevant non-secret evidence is the app version/build and crash time, `Exception Type`, `Termination Reason`, triggered thread/backtrace and matching binary UUID; for a memory kill, the corresponding EiliStore entry from a JetsamEvent is useful.
